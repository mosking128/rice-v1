# PicoC 嵌入式移植注意事项

> 基于 STM32H750VBTx 的实际移植经验总结，适用于 MCU / RTOS / 串口控制台场景的 PicoC 移植。
> 目标：最小代价稳定跑通解释器，再用清晰分层逐步扩入 REPL、脚本上传和调试能力。
>
> 如果后续切换到其它 STM32、GD32、ESP32、NXP、RTOS shell、USB CDC 或 PC 代理程序，
> 优先复用的应该是本文档里的决策和方法，而不是某几个具体文件。

## 1. 产品边界

PicoC 移植最容易返工的地方，不是编译报错，而是产品形态没收敛。
开始前先明确 4 个问题：

| 问题 | 本工程的选择 |
|------|-------------|
| 运行方式 | 默认 REPL + 整文件上传执行 |
| 输入来源 | 串口（USART1, 115200） |
| 标准库范围 | 最小可用集（mini-stdlib） |
| 错误恢复 | 脚本异常退出后回到宿主主循环（setjmp/longjmp） |

**这一步越清楚，后面越不会在入口、文件系统、标准库和调试器之间反复返工。**

## 2. 三层架构

最稳妥的移植方式不是直接改 PicoC 内核，而是拆成 3 层解耦。

```
┌───────────────────────────────────────────────────────────┐
│  应用适配层  picoc_app.c                                  │
│  REPL 状态机 · 脚本上传执行 · 控制命令 · 调试协议桥接     │
├───────────────────────────────────────────────────────────┤
│  平台层  platform_stm32h7.c / library_stm32h7.c           │
│  字符输入输出 · 文件读取 · 程序退出 · 平台库注册          │
├───────────────────────────────────────────────────────────┤
│  内核层  lex.c / parse.c / expression.c / heap.c ...      │
│  词法分析 · 语法解析 · 表达式求值 · 内存管理              │
└───────────────────────────────────────────────────────────┘
```

### 2.1 内核层（尽量不动）

PicoC 自身解释器逻辑：`lex.c`、`parse.c`、`expression.c`、`type.c`、`variable.c`、`heap.c` 等。

- 尽量少改，只做编译兼容修正和必要 bug 修复
- 不把宿主业务逻辑塞进内核

### 2.2 平台层（只做宿主边界）

负责 PicoC 和宿主环境之间的接口桥接。

关键接口：

| 接口 | 职责 |
|------|------|
| `PlatformPutc()` | 输出单个字符 |
| `PlatformGetCharacter()` | 读取单个字符（阻塞） |
| `PlatformGetLine()` | 读取一行输入（带回显和提示符） |
| `PlatformExit()` | 退出程序（longjmp） |
| `PlatformReadFile()` | 读取文件（不支持时返回错误） |
| `PlatformLibraryInit()` | 注册平台库头文件和函数 |

- 只做平台桥接，不做 REPL 协议和业务状态机
- 所有"和硬件/系统耦合"的东西都留在这里

### 2.3 应用适配层（最有价值的部分）

负责创建 PicoC 实例、驱动 REPL、管理脚本上传执行、处理控制命令、桥接调试协议。

本工程对应实现：

- `Core/Src/picoc_app.c` — REPL 状态机
- `Core/Src/main.c` — 宿主驱动入口
- `Core/Src/serial_app.c` — 串口收发适配

**结论：内核层不动 → 平台层只做边界 → 应用层负责交互和控制。**

## 3. 芯片内存分配

> 这是嵌入式移植最容易踩坑的地方。PicoC 的内存模型和 STM32H7 的多域 RAM 架构必须提前对齐。

### 3.1 STM32H750VBTx 内存域

| 内存域 | 地址范围 | 大小 | 特点 |
|--------|----------|------|------|
| Flash | `0x0800_0000` | 128 KB | 代码存储 |
| DTCM (IRAM1) | `0x2000_0000` | 128 KB | 零等待周期，最快速 RAM |
| AXI SRAM (IRAM2) | `0x2400_0000` | 512 KB | 大容量，有等待周期 |
| SRAM1 | `0x3000_0000` | 128 KB | D2 域，DMA 可访问 |
| SRAM2 | `0x3002_0000` | 128 KB | D2 域，DMA 可访问 |
| SRAM3 | `0x3004_0000` | 32 KB  | D2 域 |
| SRAM4 | `0x3800_0000` | 64 KB  | D3 域 |
| Backup SRAM | `0x3880_0000` | 4 KB   | VBAT 供电域 |

### 3.2 Linker Scatter 分区

```
LR_IROM1 0x08000000 0x20000   ; Flash: 128 KB — 代码 + 只读数据
  RW_IRAM1 0x20000000 0x20000 ; DTCM:  128 KB — 栈 + RW/ZI 数据
  RW_IRAM2 0x24000000 0x80000 ; AXI:   512 KB — RW/ZI 数据（含 PicoC 堆）
```

### 3.3 启动文件配置

```
Stack_Size  EQU  0x2000    ; 8 KB  — 主栈（Cortex-M7 硬件栈）
Heap_Size   EQU  0x20000   ; 128 KB — C 库 malloc 堆
```

### 3.4 PicoC 内存布局

PicoC 的 `HeapMemory[]` 数组内部分为两个方向增长的区域：

```
HeapMemory[HEAP_SIZE]（64 KB 静态数组，位于 BSS 段）
  ┌──────────────────────────────────────────┐
  │ 栈区（向上增长）  ←───  堆区（向下增长）  │
  │ 临时值、调用帧     持久变量、类型表、字符串 │
  │ StackFrame →       ← HeapBottom           │
  └──────────────────────────────────────────┘
```

| 配置项 | 值 | 定义位置 |
|--------|-----|---------|
| `HEAP_SIZE` | 64 KB | `picoc/platform.h`（`STM32H750_HOST` 分支） |
| `PICOC_APP_STACK_SIZE` | 64 KB | `Core/Src/picoc_app.c` |
| `BUILTIN_MINI_STDLIB` | 启用 | `picoc/platform.h` |

### 3.5 实际 RAM 占用估算

**静态分配（BSS 段）：**

| 变量 | 大小 | 所在段 |
|------|------|--------|
| `g_picoc.HeapMemory[]` | 64 KB | BSS |
| `isolated_picoc.HeapMemory[]` | 64 KB | BSS（static 局部变量） |
| `rx_dma_buffer[]` | 1 KB | BSS |
| `rx_ring[]` | 8 KB | BSS |
| `tx_ring[]` | 8 KB | BSS |
| `g_source_buffer[]` | 2 KB | BSS |
| `g_load_buffer[]` | 8 KB | BSS |
| 执行缓冲区、命令缓冲区等 | ~2 KB | BSS |
| **静态合计** | **~157 KB** | |

**动态分配（启动文件堆区）：** 128 KB

**合计峰值 RAM 需求：~285 KB**

可用 RAM：DTCM 128 KB + AXI SRAM 512 KB = 640 KB，足够覆盖。
但需要注意：

- DTCM 只有 128 KB，静态 BSS + 栈需要落在这 128 KB 里，实际可能溢出
- 两个 `HeapMemory[64KB]` 是 RAM 大头，应考虑放到 AXI SRAM

### 3.6 踩坑要点

> **CubeMX 重新生成后要检查启动文件的 Stack/Heap 大小**，避免被恢复为默认小值。

1. **主栈 8 KB 可能不够。** 如果 `Picoc_Struct` 被分配到栈上（而非 static），会导致栈溢出。本工程将 `g_picoc` 和 `isolated_picoc` 均声明为 `static`，确保其 `HeapMemory[64KB]` 落入 BSS 而非栈。

2. **两个 PicoC 实例共存时需要 128 KB BSS。** `g_picoc` 是持久 REPL 实例，`isolated_picoc` 是文件执行隔离实例，两者不会同时执行 `HeapMemory`，但生命周期内各占 64 KB。

3. **DTCM 和 AXI SRAM 的访问速度差异。** DTCM 是零等待周期，适合栈和频繁访问的数据；AXI SRAM 有等待周期，适合大块数据。PicoC 的 `HeapMemory` 对性能不敏感，放 AXI SRAM 问题不大。

4. **DMA 缓冲区必须放在 DMA 可访问的 RAM 域。** DTCM（0x2000_0000）不可被 DMA 访问。如果 DMA 缓冲区需要放在 D2 域，应使用 SRAM1/SRAM2（0x3000_0000）。本工程的 `rx_dma_buffer` 默认放在 DTCM，如果遇到 DMA 传输失败，需要检查 linker 分区或使用 `__attribute__((section(...)))` 将 DMA 缓冲区放到 SRAM1。

5. **MPU 配置** 本工程在 `MPU_Config()` 中将地址 0x0 附近设为不可访问，用于捕获空指针解引用。如果脚本代码涉及低地址内存操作，需要注意 MPU 区域限制。

## 4. 硬件能力注册

> 硬件能力不要散落在业务代码或 PicoC 内核里，集中在平台库注册文件中管理。

### 4.1 注册架构

```
PlatformLibraryInit(pc)
  ├─ IncludeRegister("stdio.h", ...)
  └─ IncludeRegister("picoc_stm32.h", &Stm32SetupFunc, &Stm32Functions[], &Stm32Defs)
       ├─ Stm32SetupFunc()     → 注册常量、句柄、GPIO 端口
       ├─ Stm32Functions[]     → 绑定 HAL 函数
       └─ Stm32Defs            → 注册结构体定义
```

本工程的落点：`picoc/platform/library_stm32h7.c`

### 4.2 注册步骤

1. 确认硬件已由 CubeMX 或宿主工程初始化好（GPIO 时钟、引脚模式、UART、DMA、中断等）
2. 在平台库文件中包含目标 HAL 头文件（`stm32h7xx_hal.h`）
3. 暴露常量和句柄：GPIO 端口（`GPIOA`~`GPIOK`）、引脚常量（`GPIO_PIN_0`~`GPIO_PIN_All`）、模式/上下拉/速度常量
4. 为 HAL 函数写极薄适配函数，将 PicoC 的 `struct Value **Param` 转为 HAL 参数
5. 在 `Stm32Functions[]` 中注册函数原型
6. 使用 `SetupCSource` 注册最小结构体定义（如 `GPIO_InitTypeDef`）
7. 在 `PlatformLibraryInit()` 中通过 `IncludeRegister()` 把头名、初始化函数、函数表和结构体定义挂到 PicoC

### 4.3 已注册内容（本工程）

| 类别 | 内容 | 注册方式 |
|------|------|----------|
| GPIO 端口 | `GPIOA`~`GPIOK`（11 个） | `VariableDefinePlatformVar`，`void *` 类型 |
| 引脚常量 | `GPIO_PIN_0`~`GPIO_PIN_15`，`GPIO_PIN_All` | `VariableDefinePlatformVar`，`int` 类型 |
| 引脚状态 | `GPIO_PIN_RESET`，`GPIO_PIN_SET` | `VariableDefinePlatformVar` |
| 模式常量 | `GPIO_MODE_INPUT/OUTPUT_PP/OUTPUT_OD/ANALOG` | `VariableDefinePlatformVar` |
| 上下拉常量 | `GPIO_NOPULL/PULLUP/PULLDOWN` | `VariableDefinePlatformVar` |
| 速度常量 | `GPIO_SPEED_FREQ_LOW/MEDIUM/HIGH/VERY_HIGH` | `VariableDefinePlatformVar` |
| 结构体 | `GPIO_InitTypeDef` | `SetupCSource` 字符串定义 |
| HAL 函数 | `HAL_GPIO_Init/DeInit/ReadPin/WritePin/TogglePin`，`HAL_Delay` | `Stm32Functions[]` 函数表 |

### 4.4 关键踩坑：GPIO 时钟使能

> **PicoC 注册了 GPIO 端口变量 ≠ GPIO 端口时钟已使能。**

本工程 CubeMX 只使能了 GPIOC、GPIOH、GPIOA 三个端口的时钟。
PicoC 脚本中写 `HAL_GPIO_Init(GPIOB, &cfg)` 会**硬故障**，因为 GPIOB 时钟未开启。

**解决方案**：在 `library_stm32h7.c` 中注册各端口的时钟使能 wrapper：

```c
static void PicocHalRccGpioClkEnable(struct ParseState *Parser,
                                     struct Value *ReturnValue,
                                     struct Value **Param, int NumArgs)
{
    (void)Parser; (void)ReturnValue; (void)NumArgs;
    uint32_t port = (uint32_t)Param[0]->Val->Integer;

    switch (port) {
        case 0: __HAL_RCC_GPIOA_CLK_ENABLE(); break;
        case 1: __HAL_RCC_GPIOB_CLK_ENABLE(); break;
        case 2: __HAL_RCC_GPIOC_CLK_ENABLE(); break;
        case 3: __HAL_RCC_GPIOD_CLK_ENABLE(); break;
        case 4: __HAL_RCC_GPIOE_CLK_ENABLE(); break;
        /* ... 按需补齐 ... */
    }
}
```

或更直接的方式：在脚本侧由用户自行调用前先在固件中预使能所有可能用到的 GPIO 端口时钟。

### 4.5 注册注意事项

- **不建议重新发明并行 API**，优先复用 HAL 原名和原参数语义
- **PicoC 无法直接使用 C 宏**，宏值需要转换成平台变量注册
- **指针类对象用 `void *` 暴露**，例如 `GPIOC` 对应 `pc->VoidPtrType`
- **结构体字段顺序必须和 HAL 侧一致**，`GPIO_InitTypeDef` 的 `Pin/Mode/Pull/Speed/Alternate` 顺序不能错
- **新增外设绑定时**，在 `library_stm32h7.c` 中追加适配函数和注册条目即可，遵循现有模式

### 4.6 验证示例

```c
// 在 picoc> 提示符下输入：
int i;
for (i = 0; i < 10; i++) {
    HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_13);
    HAL_Delay(500);
}
```

## 5. 移植顺序

不要一次把"解释器 + 标准库 + 文件系统 + 调试器"全接上，按固定顺序推进。

### 5.1 第一步：最小内核编译通过

目标：编译通过、链接通过。

优先解决：编译器兼容问题、宏定义和平台配置、堆/栈策略、`setjmp/longjmp` 是否可用。

不要急着做：文件系统、完整标准库、调试器、复杂交互界面。

### 5.2 第二步：打通单向输出

优先实现 `PlatformPutc()`，只让 PicoC 能往外打印。

- 有输出才能看到启动提示
- 有输出才能看到语法错误和运行错误
- 有输出后面调试和定位成本大幅下降

**先通输出，远比先通输入更重要。**

### 5.3 第三步：打通最小输入

再实现 `PlatformGetCharacter()` 和 `PlatformGetLine()`。

但不建议直接完全依赖 PicoC 原生交互入口。对 MCU 来说更稳的方案是：

- 宿主自己收字符
- 宿主自己维护输入缓冲和状态机
- 拼出完整源码后再交给 `PicocParse()`

### 5.4 第四步：确定统一执行入口

推荐只保留两类入口：行交互 REPL 和整段源码执行。

- REPL 输入走 `PicocParse()`
- 整文件上传也走 `PicocParse()`
- 如果源码新定义了 `main()`，再调用 `PicocCallMain()`

## 6. 入口设计

不要把上游 `picoc.c` 直接当成目标平台最终入口。
推荐模型：**宿主驱动 PicoC，PicoC 只是一个组件。**

```
1. 宿主初始化硬件和系统资源
2. 初始化串口/USB/其它 IO 通道
3. 初始化 PicoC 实例
4. 进入主循环或任务循环
5. 在循环中周期性驱动 PicoC 应用适配层
```

这种结构的好处是，无论切换到裸机主循环、RTOS 任务、USB 虚拟串口、TCP 控制台还是 Bootloader 环境，都不需要重做解释器生命周期管理。

## 7. 标准库策略

### 7.1 不要一开始追求完整 libc

嵌入式上最常见的错误路线是一开始就试图把完整标准库一次性补全。
很多接口在 MCU 上根本没意义：文件 IO、进程控制、环境变量、shell 命令执行。

### 7.2 按 3 档推进

| 档位 | 内容 | 时机 |
|------|------|------|
| A 最小可运行集 | `printf`、`getchar/gets`、`malloc/calloc/free`、`strlen/memcpy/memset` | 解释器跑起来 |
| B 常用头注册 | `stdio.h`、`stdlib.h`、`string.h`、`stdbool.h` | 脚本 `#include` 不报错 |
| C 平台扩展头 | `picoc_stm32.h`、`picoc_board.h` | 解释器稳定后 |

优先复用 PicoC 自带 `mini-stdlib`，再在平台层注册需要的头文件名。

## 8. 控制台协议

不建议完全依赖 PicoC 原生交互逻辑，宿主自己定义一层控制台协议更稳。

推荐两种模式：

- **REPL 模式**：逐行交互
- **LOAD 模式**：批量接收源码

基础控制命令：`:load`、`:end`、`:abort`、`:ping`、`:reset`

调试扩展命令：`:bkpt`、`:bkptclear`、`:cont`、`:step`、`:eval`、`:vars`、`:set`

好处：容易对接上位机、支持整文件发送、做错误恢复、切换输入通道、叠加调试协议。

**这是本工程最值得复用的移植经验之一。**

## 9. 调试能力接入

PicoC 自带 `debug.c` 框架，但"源码里有调试器"不等于"产品已支持调试"。
真正要算支持，至少打通 3 件事：内核断点表、宿主入口启用调试流程、用户能通过串口或上位机操作。

### 9.1 已落地能力

断点设置与清除、单步执行、继续执行、断点停下后表达式求值、当前作用域变量枚举、变量修改、Watch 监视变量变化。

### 9.2 推荐接入方式

- 调试器核心沿用 PicoC 原生 `debug.c`
- 应用适配层桥接调试命令
- 整文件执行时，把主实例断点复制到隔离执行实例
- 上位机通过结构化串口消息驱动 UI

### 9.3 当前边界

- 主要面向上传文件执行，不是 REPL 历史命令调试
- 断点文件名当前按 `serial_load` 处理
- 断点在单次文件运行结束后自动清空
- `:eval` 当前更适合整数表达式
- `:set` 当前主要覆盖基础标量变量
- Watch 在停点时刷新，不是运行中连续采样

**调试器框架可以早保留，但调试功能建议在最小解释器跑通后再接入。**

## 10. 错误恢复

错误恢复一定要在移植早期就想清楚。

- 脚本错误退出，不拖死宿主主循环
- 解释器异常结束后能回到控制台
- 只有底层硬件初始化失败才进入宿主致命错误处理

关键方法：通过 `PlatformExit()` + `setjmp/longjmp` 回到宿主控制流。
这套方式对 MCU、RTOS、PC 工具端都成立。

## 11. 文件系统策略

### 11.1 如果当前不依赖文件系统

明确做成"不支持"，不要中间态。

- `PlatformReadFile()` 返回不支持
- `PicocPlatformScanFile()` 返回不支持
- 源码只从串口、内存、Flash 或网络缓冲进入

### 11.2 如果后面需要文件系统

当成后续独立能力扩展，需要单独设计：源码读取、include 查找路径、错误提示里的文件名定位、缓存和内存回收。

**最小移植先不绑文件系统，晚一点接整体更稳。**

## 12. 验证路径

每换一个新平台，都按固定阶段验证，不要一上来就测复杂脚本。

| 阶段 | 验证内容 |
|------|----------|
| 1 启动 | 上电后看到欢迎信息，提示符正确显示 |
| 2 单行表达式 | `1+2`、简单变量赋值 |
| 3 多行代码块 | `if/while/for`、函数定义 |
| 4 整段源码 | 批量发送程序、自动 `main()` 调用 |
| 5 错误恢复 | 语法错误、未定义符号、缓冲区溢出、重复上传、用户主动中止 |
| 6 资源边界 | 长脚本、深递归、高频输入、重复多轮执行 |
| 7 调试能力 | 断点设置和清除、单步、表达式求值、变量查看和修改、Watch 变化刷新 |

## 13. 可复用决策清单

真正可复用的不是某个 STM32 文件，而是这些决策：

| 决策 | 说明 |
|------|------|
| 宿主驱动 PicoC | 不是反过来让 PicoC 控制宿主 |
| 平台层只做边界 | IO、退出、文件、平台库注册 |
| 应用层管理状态机 | REPL / LOAD / DRAIN 状态切换 |
| 统一 PicocParse() | REPL 和整文件共用一套执行入口 |
| 先最小可用再扩展 | 先 mini-stdlib，再逐步补头文件 |
| 文件系统后置 | 最小移植阶段不绑定文件系统 |
| setjmp/longjmp 统一错误恢复 | 对 MCU / RTOS / PC 均成立 |
| 宿主管理控制台和调试协议 | 不依赖 PicoC 原生交互逻辑 |

如果切换到其它 STM32、GD32、NXP、ESP32、RTOS shell、USB 虚拟串口或 PC 代理程序，建议沿用这套决策。
